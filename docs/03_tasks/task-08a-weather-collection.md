# Task 8a. 날씨 수집 (단기예보 수치 + 공식 특보)

상태: **실데이터 검증 통과, 사용자 승인 대기** (작성일 2026-11-16, 2차 수정 2026-11-16, 검증 2026-11-16)

## 배경
사용자 요청으로 브리핑에 **[3. 종합 평가]** 섹션(Task 8b)을 추가하기로 함 — 오늘의 기상+어제 사고 심각도를 종합한 위험지수, 교차 인사이트, 핵심 경고, 날씨 기반 "오늘의 한마디"로 구성. 이를 위해 먼저 날씨 원본 데이터가 필요하며, 이 작업(8a)은 그 수집·요약만 담당한다(위험지수 판정/AI 종합은 8b 범위).

### 조사 결과 (실 API 호출로 확인, 2026-11-16)
- 사용자가 data.go.kr에서 두 날씨 API 상품에 대해 활용신청 완료. **키는 새로 발급되는 게 아니라 기존 `DATA_GO_KR_SERVICE_KEY`가 그대로 승인됨**(2b 통계 API와 동일 키 재사용, 포털 "활용신청"은 상품별로 별도였을 뿐 키 자체는 계정 단위).
- **단기예보(`getVilageFcst`, VilageFcstInfoService_2.0)**: 실호출 성공 — `resultCode: "00" NORMAL_SERVICE`, 서울 격자(nx=60, ny=127) 기준 실제 기온/풍속 수치 수신 확인.
- **기상특보(`getWthrWrnList`)**: 최초 테스트 때는 `stnId=109`가 `NO_DATA`를 반환해 "지역코드가 틀렸을 수 있다"고 1차 결론 내렸으나, **사용자가 공식 활용가이드(`기상청21_기상특보 조회서비스_오픈API활용가이드.docx`)를 직접 내려받아 제공** — 문서 맨 뒤 `# 첨부. 지점코드` 표에 다음이 명시돼 있음:

  | stnId | 지점명 | 특보해당구역 |
  |---|---|---|
  | 108 | 서울 | **전국** |
  | 109 | 서울 | **서울, 인천, 경기도** |
  | 159 | 부산 | 부산·울산·경상남도 |
  | 143 | 대구 | 대구·경상북도 |
  | 105 | 강릉 | 강원도 |

  "지점명"은 발표 관서(지방기상청) 소재지명이고, 실제 대상 지역은 "특보해당구역" 컬럼이다. **`stnId=109`가 애초부터 맞는 코드였고, 최초의 `NO_DATA`는 그 시점에 서울·인천·경기 지역에 발효 중인 특보가 실제로 없었다는 정상 응답**이었다(에러가 아님 — 활용가이드의 에러코드표에서도 `3=NODATA_ERROR`는 "데이터없음"으로 정의돼 있어 조회 자체는 정상 처리된 것으로 확인). `fromTmFc`/`toTmFc`로 최근 5일 범위를 지정해 재확인해도 동일하게 "현재 조용한 기간"임을 재검증(반면 `stnId=108`/`159`는 같은 기간에 실제 특보 이력이 정상 수신됨 — API 자체는 정상 작동 확인).
  - 별도 엑셀(`...특보구역코드안내.xlsx`)에는 시/군 단위로 더 세분화된 `areaCode`(예: `L1100000`=서울특별시, 8자리 영숫자)도 있으나, 이건 특보 통보문 본문(`getWthrWrnMsg`)의 "해당구역" 상세 텍스트용으로 보이며 `getWthrWrnList`의 `stnId`와는 다른 체계다 — 이번 작업에서는 쓰지 않는다(필요해지면 별도 검토).
- **결론: 공식 특보(`getWthrWrnList`, stnId=109)를 8a 범위에 포함한다.** 수치 기반 추정으로 대체하지 않고, 공식 발표/해제 이력을 그대로 "공식 특보"로 표기할 수 있다 — CLAUDE.md의 "사실 확인 전 추측 금지" 원칙에 더 부합한다.

## 목표
기상청 단기예보 API에서 서울(nx=60, ny=127) 기준 오늘 하루의 기온·습도·강수확률·풍속·하늘상태·강수형태를 수집하고, 기상특보 API(stnId=109, 서울·인천·경기)에서 현재 발효 중인 공식 특보 목록을 조회해, 하루 단위로 요약한 JSON을 생성한다.

## 입력
- API 1(단기예보): `GET https://apis.data.go.kr/1360000/VilageFcstInfoService_2.0/getVilageFcst`
- API 2(특보): `GET https://apis.data.go.kr/1360000/WthrWrnInfoService/getWthrWrnList`
- 환경변수(`.env`, `dotenv_loader.py`로 로드):
  - `DATA_GO_KR_SERVICE_KEY` — 기존 키 재사용(신규 발급 없음), 두 API 모두 동일 키
  - `WEATHER_NX`, `WEATHER_NY` — 단기예보 격자 좌표, 기본값 60/127(서울). `.env.example`에 이미 추가됨
  - 특보의 `stnId=109`(서울·인천·경기)는 활용가이드로 공식 확인된 고정값이라 `.env`로 빼지 않고 코드 상수로 둔다(ponytail: 바뀔 일 없는 공식 코드를 설정값처럼 다루지 않음)
- 단기예보 파라미터: `pageNo`, `numOfRows`, `dataType=JSON`, `base_date`, `base_time`, `nx`, `ny`
- 특보 파라미터: `serviceKey`, `pageNo`, `numOfRows`, `dataType=JSON`, `stnId=109`, `fromTmFc`, `toTmFc`

## 처리 로직 개요
### A. 단기예보(수치)
1. **발표회차(base_time) 역산**: 단기예보는 하루 8회(02/05/08/11/14/17/20/23시) 발표되고, 실제 제공은 발표시각+10분경부터다. 현재 KST 시각 기준으로 "발표 후 20분 이상 지난 가장 최근 회차"를 역산한다(자정 넘어가는 경우 전날 23시 회차로 롤백). 하드코딩된 단일 회차를 쓰지 않는다 — cron 실행 시각(08:00 KST)엔 아직 08시 회차가 없으므로 05시 회차가 선택되어야 함.
2. 위 `base_date`/`base_time`, `WEATHER_NX`/`WEATHER_NY`로 API 호출(재시도: `accident_stats.py`의 `_http_get_json` 패턴 재사용 — 지수 백오프 `2**attempt*2`초, 최대 3회, 타임아웃 25초).
3. 응답 `resultCode`가 `"00"`이 아니면 즉시 에러로 중단(가짜 값으로 대체하지 않음).
4. 응답 항목을 `category`별로 모아 **오늘 날짜(`fcstDate`=조회 시점 기준 오늘)**에 해당하는 시간대만 필터링:
   - `TMP`(기온) → 최고/최저
   - `REH`(습도) → 최대
   - `POP`(강수확률) → 최대
   - `WSD`(풍속) → 최대
   - `SKY`(하늘상태코드: 1맑음/3구름많음/4흐림), `PTY`(강수형태코드: 0없음/1비/2비눈/3눈/4소나기) → 오늘 등장한 코드 집합(중복 제거, 사람이 읽을 라벨로 변환)
5. 해당 회차로 오늘 날짜 데이터가 비어있으면(예: 23시 회차처럼 다음날 위주) 한 단계 이전 회차로 1회 폴백 재조회.

### B. 기상특보(공식)
1. `stnId=109`(서울·인천·경기, 고정값), `fromTmFc`=오늘 기준 7일 전, `toTmFc`=오늘로 `getWthrWrnList` 호출. 7일로 넉넉히 잡는 이유: 특보가 며칠 전 발표돼 아직 해제 안 된 채 이어지는 경우를 놓치지 않기 위함(하루만 조회하면 "오늘 새로 발표된 것"만 보이고 "어제부터 이어지는 중"인 특보를 놓침).
2. 응답 `resultCode`가 `"03"`(NO_DATA)이면 **정상**으로 처리 — 현재 활성 특보 없음, 빈 리스트.
3. `resultCode`가 `"00"`이면 각 항목의 `title`(예: `"[특보] 제11-20호 : 2026.11.16.18:00 / 풍랑주의보 발표 (*)"`)을 정규식으로 파싱해 **특보명 목록**(`·`로 구분, 예: `["강풍주의보","풍랑주의보"]`)과 **동작**(`발표`/`해제`/`변경`)을 추출.
4. `tmFc` 기준 내림차순 정렬 후, **특보명별로 가장 최근 동작 1건만** 남긴다. 동작이 `발표` 또는 `변경`이면 "현재 발효 중", `해제`면 제외.
5. 정규식이 매치되지 않는 `title`(형식이 예상과 다름)은 추측으로 넘기지 않고 `unparsed` 목록에 원문 그대로 남긴다.
6. 그 외 `resultCode`(00/03이 아닌 실패)는 에러로 기록하되, **단기예보 결과까지 막지는 않는다** — `official_warnings`를 `null`+에러 메시지로 남기고 나머지는 정상 출력(부분 실패 허용, 기존 Task 2b의 "트렌드 보조 지표라 완벽할 필요 없음" 패턴과 동일한 취지이나 여기서는 "날씨 수치는 이미 확보했으니 특보 실패가 전체를 막을 이유는 없다"는 의미).

## 예외 처리
- 단기예보 `resultCode != "00"` → 명확한 에러로 중단(REVIEW 대체 없음 — 날씨는 사실 데이터라 추측 불가, 실패 시 8b가 "날씨 데이터 없음"으로 그 섹션만 건너뛰도록 둔다)
- 특보 `resultCode == "03"`(NO_DATA) → 정상(활성 특보 없음), 에러 아님
- 특보 `resultCode`가 00/03 둘 다 아님 → 단기예보는 그대로 출력하고 `official_warnings.error`에 메시지만 남김(부분 실패, 전체 중단 안 함)
- HTTP 5xx/타임아웃(두 API 공통) → 지수 백오프 재시도 최대 3회, 그래도 실패하면 해당 API만 위 규칙대로 처리
- 선택한 단기예보 회차에 오늘 날짜 데이터가 없음 → 이전 회차로 1회 폴백, 그래도 없으면 에러
- 단기예보 필드 누락(category 일부가 응답에 없음) → 해당 summary 필드만 `null`로 두고 나머지는 정상 출력
- 특보 `title` 정규식 미매치 → `unparsed`에 원문 보존, 추측으로 분류하지 않음

## 사용할 라이브러리
- `urllib.request`, `urllib.parse`, `json`, `re`, `datetime`, `os` — 전부 표준 라이브러리. `accident_stats.py`의 재시도 함수와 동일 패턴을 그대로 재사용(새로 만들지 않음, ponytail: 이미 있는 걸 복붙 수준으로 가져다 씀).
