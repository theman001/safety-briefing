# 01. 아키텍처 (초안)

> 상태: **데이터 소스/운영 파라미터 확정됨** (2026-11-13). Task별 세부 구현 설계는 `/plan-task`에서 진행.

## 데이터 흐름

```
[1. 수집]  네이버 뉴스 API (재설계 — naver.py는 참고용)
           + 공공데이터 API (KOSHA SIF 아카이브 + 사고재해자수 통계)
               │
               ▼
[2. 정제]  날짜 필터 → 중복 제거 → 규칙 기반 1차 분류
           → briefing_candidates.json (사고/안전동향/정비기술 후보)
               │
               ▼
[3. AI 요약]  DeepSeek API로 후보 기사/사례를 구조화 요약
           (설비/업종, 사고유형, 추정원인, 교훈 포인트)
               │
               ▼
[4. 전송]  Telegram Bot API로 매일 지정 시각 푸시
               │
               ▼
[5. 스케줄링]  Oracle Cloud 인스턴스 cron (또는 systemd timer)
           매일 1회 배치 실행, 상시 프로세스 없음
```

## 인프라 제약과 대응

| 제약 | 대응 |
|---|---|
| RAM 1GB | 상시 서버 프로세스 금지, cron 배치 스크립트로만 실행. 브라우저 크롤링 금지, HTTP API/RSS만. |
| 저사양 CPU | 분류는 가벼운 규칙 기반(정규식/키워드)으로 처리(이미 `naver.py`에 구현), ML 모델 로컬 추론 없음 — AI 요약은 DeepSeek API에 위임. |
| 외부 API 쿼터/장애 | 재시도(backoff) + 실패 시 사용 가능한 부분만으로 브리핑 전송, 전체 실패 시 오류 알림. |
| 비용 | DeepSeek은 저가 모델 위주 사용, 호출량은 "전날 후보 기사" 건수로 제한(전체 원문 재크롤링 없음). |

## 단계별 상세

### 1. 수집 (Collect)
- **뉴스**: 네이버 뉴스 검색 API. Task 1에서 처음부터 재설계 (naver.py는 쿼리 세트/분류 키워드 등 참고 자료로만 사용). 산업별 쿼리 세트로 검색 → pubDate 기준 "전날" 필터 → URL/제목 유사도 기반 중복 표시 등의 접근은 유효하지만, 구현은 새로 짠다.
- **공공데이터** (확정, data.go.kr·KOSHA 제공):
  - **사망사고 고위험요인(SIF) 아카이브 조회서비스** (데이터셋 15161362) — 사망·중상해 사례를 고위험작업(Potential)·재해유발요인(Precursor)별로 정리, 키워드 검색 지원, JSON, 이용제한 없음.
  - **산업중분류별 발생형태별 사고재해자수** — 통계 데이터. 사례 단위가 아니므로 브리핑 본문보다는 "최근 트렌드" 보조 지표로 활용(예: 특정 업종 사고 증가 여부 체크).
  - → data.go.kr 회원가입 + 활용신청(인증키 발급) 필요 — **사용자가 아직 미보유, 선행 작업**.

### 2. 정제 (Normalize & Classify)
- 산업/설비 키워드 매칭 → 사고 강도 키워드 → 분류 레이블(INCIDENT_REPORT/FOLLOWUP/SAFETY_TREND/MAINTENANCE_TECH/REVIEW/EXCLUDED) → 점수/근거 기록. 규칙 세부는 Task 1 재설계 시 `/plan-task`로 확정(naver.py의 기존 키워드 세트를 출발점 참고 자료로 검토).
- SIF 아카이브 등 공공데이터는 이미 정형 데이터이므로 별도 텍스트 분류 없이 스키마 매핑만 필요. 통계 데이터는 집계 비교(전주/전월 대비)만 수행.
- 원칙: **사실 확인 전 사고 원인/발생일을 단정하지 않음**. 애매한 건 REVIEW로 보류.

### 3. AI 요약 (Summarize)
- DeepSeek API에 `briefing_candidates.json`(사고/안전동향/정비기술 후보)을 구조화 프롬프트로 전달. **DeepSeek API 키 미보유 — Task 4 착수 전 사용자가 발급 필요.**
- 출력 형식(안): 업종 → 사고유형 → 핵심 사실 → (확인된 경우만) 추정 원인/후속조치 → 정비·설비 관점 교훈.
- REVIEW/EXCLUDED 항목은 요약 대상에서 제외(토큰 절약).

### 4. 전송 (Deliver)
- Telegram Bot API `sendMessage` (urllib 직접 호출, SDK 불필요). **봇 토큰/채팅ID 미보유 — Task 5 착수 전 사용자가 `@BotFather`로 봇 생성 필요.**
- **수신자는 1명이 아니라 목록(최대 10명)** (사용자 결정, 2026-11-16) — Bot API는 브로드캐스트 기능이 없어 `chat_id` 목록을 순회해 각각 `sendMessage` 호출. 한 명 전송 실패가 다른 수신자 전송을 막지 않음, 수신자별 성공/실패를 따로 기록.
- 메시지 길이 제한(4096자) 고려 — 업종/건수별로 분할 전송 또는 요약 압축.
- 전송 실패 시 재시도 + 로그.

### 5. 스케줄링 (Schedule)
- Oracle Cloud 인스턴스의 cron, **매일 08:00 KST** 실행.
- 실행 로그는 로컬 파일로 남기고, 주기적으로 정리(디스크/메모리 누적 방지).
