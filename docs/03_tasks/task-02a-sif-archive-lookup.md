# Task 2a. SIF 아카이브 키워드 기반 사례 조회

상태: **보류 (사용자 결정, 2026-11-16).** 작성일 2026-11-13.

## 최종 결과 — 보류 결정 사유
실제 발급받은 `DATA_GO_KR_SERVICE_KEY`로 2026-11-13과 2026-11-16, 키워드/업종코드를 바꿔가며 재확인했지만 매번 동일하게 실패:
```
NO_OPENAPI_SERVICE_ERROR (returnReasonCode 12) "해당 오픈API 서비스가 없거나 폐기됨"
```
- 같은 키로 Task 2b(odcloud API)는 성공했으므로 **키 자체는 유효** — 이 서비스(`apis.data.go.kr/B552468/sifArchive`) 쪽 문제로 확인.
- data.go.kr 카탈로그 문서(`15161362/openapi.do`)는 2026-11-13/11-16 사이 글자 하나도 안 바뀜 — "업데이트 주기: 실시간"으로 정상 게시 중인데 실제 게이트웨이만 죽어있는 모순 상태. KOSHA/data.go.kr 쪽 백엔드 장애로 추정되나 확정은 불가(추측 금지 원칙).
- 사용자 결정: 지금 당장 고칠 수 있는 범위 밖이라 **보류**, Task 4(DeepSeek 요약)로 진행. Task 3(소스 통합)은 이미 2a 블로커를 감안해 범위가 재정의됨(`task-03-daily-briefing-merge.md` 참고).
- 재개 조건: data.go.kr 쪽에서 이 서비스가 복구되거나, 사용자 마이페이지에서 승인상태/End Point가 문서와 다르다는 게 확인되면 재시도.

## 조사 결과 요약 (중요 — 당초 가정과 다름)
`docs/01_architecture.md`는 이 데이터셋을 "일일 신규 사고 피드"로 가정했으나, 실제 API(`data.go.kr/data/15161362/openapi.do`)는 **날짜 필터가 없는 키워드 검색형 API**다:
- 엔드포인트: `GET https://apis.data.go.kr/B552468/sifArchive`
- 필수 파라미터: `serviceKey`, `callApiId`(고정값 `1170`), `cateSeCd`(업종 구분 코드), `disasterOverview`(재해유형 **검색어**, 예: "사다리"), `pageNo`, `numOfRows`
- 응답은 JSON(`header`/`body` 구조)이나, 세부 필드명(사고유형/고위험요인/교훈 등)은 문서에 없음 — 실호출 전까지 "확인 안됨"
- `cateSeCd` 코드값 체계(업종 구분이 무엇을 의미하는지)도 문서에 없음

→ 이 작업은 "오늘의 신규 사고"가 아니라 **Task 1(뉴스)에서 찾은 사고의 업종/재해유형 키워드로 과거 유사 사례·교훈을 보강 조회**하는 용도로 재정의한다.

**구현 착수 시점 추가 확인(2026-11-13, 더미 키로 1회 호출)**: `serviceKey=TESTKEY`(가짜 값)로 실제 호출 시 `NO_OPENAPI_SERVICE_ERROR`(returnReasonCode 12, "해당 오픈API 서비스가 없거나 폐기됨", HTTP 400, XML 응답)를 받았다. 가짜 키로 인한 라우팅 단계 거부인지, 서비스 자체가 비활성 상태인지는 **구분 불가** — 실제 발급된 `DATA_GO_KR_SERVICE_KEY`로만 확정 가능. 추측하지 않고 REVIEW로 남겨둔다.

## 목표
Task 1 산출물(또는 CLI로 직접 준 키워드)의 업종/재해유형 키워드로 SIF 아카이브를 조회해, 유사 과거 사례 1~3건(고위험요인/재해유발요인/교훈 포인트)을 보강 자료로 가져온다.

## 입력
- API: `GET https://apis.data.go.kr/B552468/sifArchive`
- 환경변수: `DATA_GO_KR_SERVICE_KEY` (파일에 평문 기록 금지)
- 호출 파라미터: `callApiId=1170`(고정), `cateSeCd`(값은 1차 실호출로 실측), `disasterOverview`(키워드), `pageNo=1`, `numOfRows`(기본 10)
- 키워드 입력: Task 1이 아직 별도 세션에서 재설계 중이라 출력 필드를 확정할 수 없으므로, **이 작업은 Task 1 출력에 의존하지 않고 CLI 인자(`--keyword`, `--cate-code`)로 독립 테스트 가능하게 설계**. Task 1 연동은 양쪽 완료 후 Task 3(통합)에서 처리.

## 처리 로직 개요
1. `cateSeCd` 허용값/의미를 1차 실호출로 확인(코드 없이 호출 시 에러 여부, 또는 포털 코드표 존재 여부 탐색).
2. `disasterOverview`에 키워드 1개 전달, `pageNo`/`numOfRows`로 페이징 조회.
3. 응답 JSON의 `header.resultCode` 확인(성공/실패 판별 — 정확한 성공 코드 값은 실호출로 확인).
4. `body`의 item 리스트를 사례 단위로 추출. 필드 매핑은 1차 실호출 샘플로 확정 후 이 문서에 반영(이번 설계에는 가짜 필드명 기재하지 않음).
5. 결과 0건은 정상 케이스(에러 아님)로 "관련 사례 없음" 처리.

## 출력
- `sif_cases_<keyword>.json`: 원본 응답 + 추출된 사례 필드(필드명은 실호출 후 확정)
- 독립 검증 단계 산출물이며, Task 3 통합 시 포맷 조정 가능

## 예외 처리
- 인증키 미승인/만료(에러코드 20/30/31 추정, 실호출로 확인) → 즉시 실패, 재시도 안 함(키 문제는 재시도 무의미)
- HTTP 5xx/타임아웃 → 지수 백오프 재시도 최대 3회(`naver.py` 패턴과 동일)
- 검색 결과 0건 → 정상 종료, "관련 사례 없음"으로 표시
- `cateSeCd` 코드 불명/무효 → 에러 메시지 그대로 기록, REVIEW 표시(사실 확인 전 코드 의미 단정 안 함)

## 사용할 라이브러리
- `urllib.request`, `urllib.parse`, `json` — 표준 라이브러리로 충분. 새 의존성 불필요.
