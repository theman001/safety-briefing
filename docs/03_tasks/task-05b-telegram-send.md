## 목표
`output/summarized_briefing_<date>.json`을 사고/안전동향 두 섹션으로 나눠 포맷하고, `subscribers.json`에 등록된 구독자 전원에게 텔레그램으로 전송한다. 한 명 실패가 나머지 전송을 막지 않는다.

## 입력
- `output/summarized_briefing_<date>.json` — Task 4 실제 출력. 각 항목: `{"title","link","classification","industry","incident_type","key_facts","probable_cause","maintenance_lesson","needs_review"}`. `classification`은 `INCIDENT_REPORT`/`INCIDENT_FOLLOWUP`/`SAFETY_TREND`/`MAINTENANCE_TECH`/`LAW_POLICY` 중 하나(news_classify.py의 `incidents`/`safety_and_maintenance` 분류와 동일 — Task 3이 이미 이 둘로만 걸러서 넘겨줌, 새 분류 로직 불필요).
- `subscribers.json` — Task 5a가 관리하는 구독자 목록 (이 작업은 읽기만 함, 쓰지는 않되, 403 발생 시 예외적으로 제거는 함 — 아래 참고)

## 처리 로직 개요

### 1. 포맷터 — classification → 섹션 2개
실데이터(2026-11-12, 59건)로 실측: `INCIDENT_REPORT`+`INCIDENT_FOLLOWUP` 19건, `SAFETY_TREND`+`MAINTENANCE_TECH`+`LAW_POLICY` 40건. 둘 다 아래 "기사 블록" 포맷으로 합치면 각각 5,501자 / 11,108자 — **둘 다 4096자를 넘는다.** 즉 분할은 드문 경우가 아니라 매일 일어나는 정상 동작으로 설계해야 한다.

- `INCIDENT = {"INCIDENT_REPORT", "INCIDENT_FOLLOWUP"}` → 섹션 제목 `"오늘의 사고 ({date}, {n}건)"`
- `TREND = {"SAFETY_TREND", "MAINTENANCE_TECH", "LAW_POLICY"}` → 섹션 제목 `"안전동향·정비기술 ({date}, {n}건)"`
- 그룹에 0건이면 그 섹션 자체를 만들지 않음(빈 메시지 전송 방지). 둘 다 0건이면 "전송할 내용 없음"으로 간주.
- 각 그룹 내 기사는 원본 순서 유지, 1부터 번호 매김(분할돼도 번호는 전체 섹션 기준으로 계속 — 1/2 조각이라도 1~19 그대로).

**기사 블록 포맷** (평문, `parse_mode` 없음. **사용자 피드백(2026-11-16) 반영: 이모지로 필드 구분** — 업종/원인/교훈 등이 글자만으로는 구분이 잘 안 된다는 피드백):
```
{i}. {title}{" ⚠️ 검토 필요" if needs_review else ""}
🏭 {industry}{" · 🔧 " + incident_type if incident_type else ""}

🔍 원인: {probable_cause 또는 "확인되지 않음(조사 중)"}

```
섹션 제목에도 구분용 이모지 추가: `🚨 오늘의 사고 (...)` / `📊 안전동향·정비기술 (...)`.

`probable_cause`가 `null`이면 지어내지 않고 "확인되지 않음(조사 중)"으로 고정 표기 (CLAUDE.md 날조 방지 원칙 그대로 전달 단계까지 유지). `incident_type`/`maintenance_lesson`도 `null`일 수 있음(실측: 59건 중 각각 33건/34건 null) — 빈 값을 지어내거나 "없음"으로 채우지 않고 **해당 부분/줄 자체를 생략**.

### 2. 분할 로직 (기사 경계 기준, 글자수 절단 아님)
섹션 `body`가 4096자를 넘으면, 기사 블록 하나를 통째로 유지하면서 그리디(greedy)하게 4096자 이하 청크로 나눈다 — 문장 중간이 아니라 기사 사이에서만 끊는다. 청크가 2개 이상이면 각 청크의 메시지 제목에 `" ({k}/{총 청크 수})"`를 붙인다(예: `"오늘의 사고 ({date}, 19건) (1/2)"`). 기사 블록 자체가 4096자를 넘는 극단적 경우(현재 데이터에는 없음)는 그 블록만 강제로 글자수 절단 — 발생 시 로그로 남김.

### 3. 전송
1. `subscribers.json`에서 현재 `chat_id` 목록을 읽는다. 비어있으면 "구독자 없음" 경고만 남기고 정상 종료(exit 0).
2. 위 포맷터로 섹션(청크 포함) 목록을 만든다. 둘 다 0건이면 "전송할 내용 없음" 경고, 정상 종료(exit 0).
3. `chat_id` 목록을 순회. 각 chat_id에 섹션(청크)을 순서대로 전송. HTTP 429/5xx는 지수 백오프 재시도(최대 3회). **같은 chat_id에서 한 번 실패하면 남은 섹션은 건너뛰고 다음 chat_id로 넘어간다.**
4. **전송 중 403(bot blocked)을 받으면 그 chat_id를 `subscribers.json`에서도 제거한다** — Task 5a의 폴링과 별개로, 실제 전송 실패 시점에도 유령 구독자를 즉시 정리하는 2차 안전망.
5. 수신자별 성공/실패를 기록. 전원 실패면 비정상 종료(exit 1), 1명 이상 성공하면 정상 종료.

## 사용자 확인(2026-11-16): 상세 유지 vs AI 축약, 상세 유지로 결정
4096자 초과가 포맷 품질 문제가 아니라 볼륨 문제임을 실측으로 확인 후 질문: 안전동향 40건=11,108자(건당 평균 278자)를 4096자 안에 넣으려면 건당 평균 102자로 줄여야 하는데, 이는 원인/교훈을 거의 다 버려야 하는 수준(이 프로젝트의 핵심 목적과 충돌). 사용자는 **지금 설계(기사단위 분할, 상세 유지)를 선택** — 도참 지식(원인/교훈)은 손실 없이, 섹션당 메시지 수가 늘어나는 쪽을 택함. 추가 AI 축약 단계는 도입하지 않음.

## 버그 발견·수정(2026-11-16): UTF-16 길이 vs Python `len()`
이모지 포맷 적용 후 실전송에서 `HTTP 400: message is too long` 발생 — Python `len()`으로는 4096자 미만(본문 4074자)이었는데도 텔레그램이 거부함. 원인 2가지:
1. 텔레그램의 4096자 한도는 **UTF-16 코드유닛 기준**인데, 이번에 추가한 이모지(🚨📊🏭🔧📝🔍💡🔗)가 대부분 서로게이트 페어 문자라 Python `len()`(코드포인트 수)보다 실제로 더 길게 집계됨.
2. `chunk_blocks()`가 **본문(body)만** 4096자 기준으로 자르고, 실제 전송 시 붙는 "제목+빈줄"은 계산에 안 들어가 있었음 — 둘이 겹쳐 실제 전송 직전에야 초과가 드러남.
수정: `tg_len()`(UTF-16 코드유닛 계산 함수) 추가, 청크 분할 기준을 `len()` → `tg_len()`으로 전환, 제목 오버헤드용 여유분(`TITLE_OVERHEAD_RESERVE=200`)을 본문 분할 한도에서 미리 빼둠(`BODY_LIMIT = 4096 - 200`). 재검증: 실제 전송 성공(4/4건), peak RSS 28MB/20초.
