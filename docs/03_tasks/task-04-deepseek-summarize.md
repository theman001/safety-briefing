## 피드백 반영 (6차, 2026-11-20) — Task 3b 원문 전체(full_text) 활용

### 배경
Task 3b(`fulltext_fetch.py`, 완료·승인됨)가 `daily_briefing_enriched_<date>.json`에 기사별 `full_text`(원문 전체, 매칭 안 되면 null)를 생성해두는데, Task 4는 아직 이걸 안 쓰고 여전히 `daily_briefing_<date>.json`(description만)을 읽는다. Task 3b 설계 당시 "Task4 쪽 변경은 별도 /reflect로 다룬다"고 명시해뒀던 부분.

### 설계
1. **입력 경로 우선순위**: 같은 날짜의 `daily_briefing_enriched_<date>.json`이 있으면 그걸 쓰고, 없으면(Task 3b를 안 돌렸거나 실패한 경우) 기존 `daily_briefing_<date>.json`으로 자연 폴백 — Task 3b가 선택적 단계라는 전제를 유지한다. `--date` 없이 "최신 파일 찾기"도 동일 원칙: `daily_briefing_2*.json`(숫자로 시작 — "enriched" 변형과 글롭 패턴이 안 겹치게)으로 최신 날짜를 먼저 찾고, 그 날짜의 enriched 버전이 있으면 그걸 우선 채택.
2. **payload에 `full_text` 필드 추가**: `build_request_payload()`가 기존 `description` 옆에 `full_text`(string|null, Task 3b가 안 돌았으면 키 자체가 없을 수 있어 `.get()`으로 안전하게 처리)를 그대로 추가 전달. 필드를 통합(description 제거)하지 않고 둘 다 보내는 이유: 모델이 매칭 실패(`full_text: null`)를 쉽게 구분할 수 있고, 구조 변경 위험을 최소화(YAGNI).
3. **SYSTEM_PROMPT 수정**: 원인 단정 금지 지시 문장에 "`full_text`가 있으면 description보다 우선 근거로 쓰고, 없으면 title/description만으로 판단"을 추가. 분류 교정 지시 문장의 "title/description 본문을 직접 읽고"도 "(또는 있으면 full_text)"를 추가해 교정 판단에도 원문 전체를 반영하게 한다.
4. **비용 트레이드오프**: `full_text`는 기사당 평균 1,000~2,000자(최대 약 4,000자 관찰됨, Task 3b 검증 기록 참고)로 `description`(100~200자)보다 훨씬 크다 — 입력 토큰이 유의미하게 늘어날 것으로 예상됨. 실데이터 검증에서 `prompt_tokens`를 변경 전/후 직접 비교해 증가폭을 사용자에게 보고한다(추측 아니라 실측).

## 입력 스키마 관련 메모

Task 3가 최종 컨펌되며 스키마가 바뀌면, 이 문서의 "입력" 절과 파싱 부분만 조정하면 된다(DeepSeek 호출 로직 자체는 영향 없음).

## 목표
`daily_briefing_<date>.json`의 각 기사(최대 63건 규모)를 DeepSeek API 1회 호출로 구조화 요약(업종/사고유형/핵심사실/추정원인(확인된 경우만)/정비·설비 교훈)해 `summarized_briefing_<date>.json`을 만든다.

## 입력
- `output/daily_briefing_<date>.json` — Task 3 실제 출력. 필요 필드: `title`, `description`, `link`, `classification`, `matched_industry_terms`, `stat_context`(있으면)
- API: `POST https://api.deepseek.com/chat/completions` (OpenAI 호환 포맷, 공식 문서 `api-docs.deepseek.com` 2026-11-16 확인)
  - 모델: `deepseek-flash` (저가 모델 — CLAUDE.md "저가 모델 위주 사용" 원칙. `deepseek-v4-pro`는 입력 4배/출력 3.3배 비쌈, 이 작업엔 과함)
  - 인증: 헤더 `Authorization: Bearer ${DEEPSEEK_API_KEY}`
  - **`"thinking": {"type": "disabled"}`로 명시 설정** — 기본값은 thinking 활성화인데, 이건 추론이 필요한 작업이 아니라 이미 분류된 기사의 구조화 추출이라 thinking 끄면 토큰(비용)과 지연이 줄어듦(의도적 설계 결정, 문서에 남김)
  - `response_format: {"type": "json_object"}`로 JSON 강제
- 환경변수: `DEEPSEEK_API_KEY` (`.env`, `dotenv_loader.py`로 로드 — 기존 패턴과 동일)

## 처리 로직 개요
1. `load_dotenv()` → `DEEPSEEK_API_KEY` 확인.
2. `daily_briefing_<date>.json` 로드. 입력 0건이면 **API 호출 자체를 스킵**하고 빈 요약으로 정상 종료(비용 절약, 에러 아님).
3. 전체 기사를 **1회 호출**로 처리(63건 전체 텍스트 ≪ 1M 컨텍스트, 분할 불필요 — 나중에 건수가 크게 늘면 그때 청크 분할 추가, 지금은 YAGNI).
4. 프롬프트 설계:
   - system: "사실 확인 전 사고 원인/발생일을 단정하지 않는다. 원문에 명시되지 않은 원인은 `probable_cause: null`로 두고 `needs_review: true`로 표시하라" 등 프로젝트 원칙을 명시적으로 지시.
   - system: **"입력 기사에 `stat_context`가 있으면, `maintenance_lesson`에 그 `top_event_types` 중 최소 1개 용어를 구체적으로 언급해 업종 통계와 연결하라"**를 명시적으로 지시 (2026-11-16 1차 실데이터 검증에서 발견한 문제의 수정 — 아래 "검증 기록" 참고. 데이터를 모델에게 주는 것과 "그걸 쓰라고 지시하는 것"은 별개라는 걸 실데이터로 확인).
   - user: 기사 배열을 `index`(0부터, 원본 순서 보존용) + title/description/classification/matched_industry_terms/stat_context만 추려 JSON으로 전달. (원문 전체 재크롤링 없음 — 이미 가진 title/description만 사용, 아키텍처 원칙과 일치)
   - 응답 형식 지시: `{"summaries": [{"index": int, "industry": str, "incident_type": str|null, "key_facts": str, "probable_cause": str|null, "maintenance_lesson": str|null, "needs_review": bool}, ...]}` — 반드시 입력과 같은 건수.
5. 응답 JSON 파싱 → `index`로 원본 기사와 매칭해 `title`/`link` 등을 다시 붙인다(모델이 지어낼 수 있는 필드는 모델 출력에서 가져오지 않고 전부 원본에서 가져옴 — 사실 왜곡 방지).
6. **입력 건수 == 출력 건수** 검증(Task 3와 동일한 유실 방지 원칙). 불일치 시 에러로 처리.

## 예외 처리
- `DEEPSEEK_API_KEY` 없음 → 즉시 종료(코드 2), 명시적 메시지
- HTTP 401(인증 실패) → 즉시 실패, 재시도 안 함
- HTTP 429/5xx/타임아웃 → 지수 백오프 재시도 최대 3회(`naver.py` 패턴)
- 응답이 JSON이 아니거나 `summaries` 키 없음 → 명시적 에러로 중단(부분 결과로 얼버무리지 않음)
- 입력 건수 ≠ 출력 건수 → 에러로 처리, 실패 보고(1차 구현에서는 개별 재시도 없음 — 전체 재실행 유도, YAGNI)
- `daily_briefing_<date>.json` 없음 → 에러 종료(Task 3 먼저 실행 필요)
- 입력 0건 → API 호출 스킵, 빈 결과로 정상 종료

### 처리 로직 변경 — SYSTEM_PROMPT 2단계 교체
기존 2단계 지시:
> "1단계에서 중복으로 걸리지 않은 기사만 대상으로 저관련성/저중요도를 좁게 적용한다: 순수 행정 반복 공지(지자체·기관의 정기 안전교육 실시 안내, 단순 행사 참석·개최 소개, 제품/기업 홍보가 주목적인 기사)만 dropped를 true로 표시한다. [...] dropped 여부가 애매하면 dropped를 false로 유지한다(과잉 제거보다 과소 제거가 낫다)."

신규 2단계 지시(교체):
> "2단계(중요도·관련성 판정) — 1단계에서 중복으로 걸리지 않은 기사 중, 최종 classification이 INCIDENT_REPORT/INCIDENT_FOLLOWUP이 **아닌** 기사(SAFETY_TREND/MAINTENANCE_TECH/LAW_POLICY)만 이 저관련성 판단의 대상이다 — 실제 사고로 교정된 기사는 정보가 부족해도 조기발견 목적상 저관련성으로 제외하지 않는다(1단계 중복 판정만 적용된다).
> 이 프로젝트의 핵심 목적은 '어떤 안전사고가 있었는지, 원인이 무엇인지, 거기서 얻는 정비·설비 교훈'이다. 다음에 해당하면 dropped를 true로 표시한다: 지자체·공공기관·기업·정치인이나 지자체장이 주체가 되어 안전 교육·점검·캠페인·협약·포상·수상·훈련을 '실시했다/강화한다'고 소개만 하는 홍보·행정성 기사('정기' 여부와 무관하게 적용). 정치인·지자체장이 안전 현장을 방문·점검하는 것을 정치적 행보로 다루는 기사도 포함한다.
> 반대로 다음은 dropped를 false로 유지한다(정치인이 관여해도 제외하지 않는다): 구체적인 정책·제도 변화(시행령/평가기준/법 개정의 실제 내용), 노동법·중대재해처벌법 등 법적 쟁점에 대한 공방이나 판단, 안전 기술·관리체계의 신규 도입이나 전환, 점검에서 실제로 발견된 위반사항이나 구체적 예방조치, 구체적 위험요인 분포를 보여주는 통계(예: 사업장 규모·사고 유형별 집중도)처럼 설비·안전관리에 실질적으로 참고할 '내용'이 있는 기사.
> 이 저관련성 판단이 애매하면(홍보성인지 실질적 내용이 있는지 구분이 안 되면) dropped를 true로 둔다 — 이 범위(비사고성 트렌드/정책 기사)에 한해서는 과소 제거보다 과잉 제거가 낫다. needs_review는 이 판단과 무관하다(기존과 동일, probable_cause 불확실성 전용)."

핵심 변경 3가지:
1. **대상 범위를 비사고 기사로 한정** — 실제 사고(INCIDENT_REPORT/FOLLOWUP)는 이 저관련성 기준으로 절대 제외되지 않도록 명시(3차 검증 때 확립된 "과잉 제거가 조기발견 목적을 해친다"는 원칙을 사고 기사에는 그대로 유지하면서, 비사고 기사에만 선택적으로 엄격화).
2. **홍보·행정성 기사 범위 확장** — "정기" 한정 해제, 정치인/지자체장의 안전 행보 기사를 명시적 drop 대상으로 추가.
3. **애매할 때의 기본값을 반전** — 비사고 기사에 한해 "애매하면 유지"를 "애매하면 제외"로 바꾼다. (단, 사고 여부 자체가 애매한 경우는 여전히 분류 단계에서 INCIDENT_*로 유지되므로 이 반전의 영향을 받지 않음 — 이중 안전장치.)

`parse_summaries()`/`split_dropped()`/`build_request_payload()`는 코드 변경 없음(SYSTEM_PROMPT 문자열만 교체).

## 피드백 반영 (9차, 2026-11-20) — 정치 분류 기준을 "직접/간접 영향"으로 일반화, 법안 발의 단계도 drop

### 배경
배포 후 실제 발송(2026-11-19)된 "안전동향·정비기술" 섹션에 "추미애 경기지사, 축산진흥센터·소방학교 안전점검…" 기사가 그대로 포함돼 있었음 — 5차에서 이미 "정치인·지자체장의 안전 현장 방문·점검을 정치적 행보로 다루는 기사"는 drop 대상으로 명시한 유형인데 이번엔 걸러지지 않음. 이미 알고 있는 run-to-run 변동성 범위로 보고 이 사례 자체에 대한 별도 조치는 하지 않음.

사용자가 이를 보고 5차의 "정치" 기준을 더 일반화된 원칙으로 재정리 요청:
> "정치인이 ~~했다"의 내용은 "정치"로 분류됨. 저 행위 이후에 실질적으로 정책에 반영되는 내용, 즉 **실무관점 직접적 영향**이 있는 내용만 필터링해서 봐야 함.
> - 간접적 영향(drop): 정치인이 안전 점검을 했다, ~~한 법안을 냈다.
> - 직접적 영향(keep): 산업안전법이 개정되어 !!에서 @@로 변경됨 — 이런 직접적 내용을 동향으로 받으려 함.

**핵심 발견**: 기존 5차 SYSTEM_PROMPT의 keep 예외 조항("구체적인 정책·제도 변화(시행령/평가기준/법 개정의 실제 내용)")이 "법안을 냈다/발의했다"(아직 시행 전인 입법 추진·예고 단계)와 "법이 실제로 개정되어 시행됐다"(이미 확정, 구체적 전/후 변화 있음)를 구분하지 않고 있음 — 전자도 느슨하게 "정책·제도 변화"로 읽혀 keep될 위험이 있었음(이번에 실제로 샌 "추미애" 사례는 이 조항이 아니라 "현장방문" 조항 쪽 변동성이지만, 같은 "간접 vs 직접" 원칙으로 재정리하면서 법안 발의 구분도 같이 명확히 함).

### 사용자 결정 — SYSTEM_PROMPT 2단계 keep 예외 조항 교체
기존 keep 예외 조항:
> "반대로 다음은 dropped를 false로 유지한다(정치인이 관여해도 제외하지 않는다): 구체적인 정책·제도 변화(시행령/평가기준/법 개정의 실제 내용), 노동법·중대재해처벌법 등 법적 쟁점에 대한 공방이나 판단, 안전 기술·관리체계의 신규 도입이나 전환, 점검에서 실제로 발견된 위반사항이나 구체적 예방조치, 구체적 위험요인 분포를 보여주는 통계(예: 사업장 규모·사고 유형별 집중도)처럼 설비·안전관리에 실질적으로 참고할 내용이 있는 기사."

신규(교체):
> "정치/행정 관련 기사를 판단할 때 핵심 기준은 실무 관점에서 **직접적 영향**(이미 확정되어 실제로 적용되는 구체적 변화)인가, **간접적 영향**(아직 효력이 발생하지 않은 행위·선언·추진 단계)인가이다. 간접적 영향은 dropped를 true로 둔다: 정치인·지자체장의 안전 현장 방문·점검·캠페인·협약·포상, 그리고 **법안을 발의했다/제안했다/추진하겠다고 밝혔다처럼 아직 시행되지 않은 입법 예고·추진 단계**도 여기 포함한다(실제로 바뀐 것이 없으므로). 반대로 다음은 직접적 영향이므로 dropped를 false로 유지한다(정치인이 관여해도 제외하지 않는다): **이미 확정·시행되어 구체적으로 무엇이(개정 전 → 개정 후) 바뀌었는지가 명시된** 법 개정·시행령·평가기준 변경, 노동법·중대재해처벌법 등 법적 쟁점에 대한 공방이나 판단(쟁점 자체가 실무에 영향), 안전 기술·관리체계의 신규 도입이나 전환, 점검에서 실제로 발견된 위반사항이나 구체적 예방조치, 구체적 위험요인 분포를 보여주는 통계(예: 사업장 규모·사고 유형별 집중도)처럼 설비·안전관리에 실질적으로 참고할 내용이 있는 기사."

핵심 변경: "정책·제도 변화"라는 keep 조건에 **"이미 확정·시행됐고 구체적 전/후 변화가 있어야 한다"**는 조건을 명시적으로 추가하고, "법안 발의/추진 선언" 단계를 정치인 현장방문과 같은 "간접적 영향" drop 범주에 명시적으로 포함시킴.

### 위험 요소
